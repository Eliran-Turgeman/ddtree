# Step 6.2: frozen cross-domain validation

## Status

**Recommendation: GO WITH CAVEATS.**

Pairwise-K16 improved online matched-token acceptance and throughput at every
tested budget on GSM8K, MATH500, HumanEval, controlled-history MT-Bench, and
native-trajectory MT-Bench. All prompt/problem/conversation-clustered 95%
confidence intervals for both absolute matched-token gain and absolute
tokens/second gain exclude zero.

Task scores varied by a few problems across target tensor shapes. There was no
consistent quality loss that tracked the Pairwise acceptance gain, but the
generated outputs are not task-identical: MATH500 differences ranged from -4 to
+3 correct problems for Pairwise versus Unary, and HumanEval differences ranged
from -2 to +4 passing problems. This is evidence against a large systematic
quality regression, not a statistical equivalence test.

Step 6.2 is frozen. Do not tune the scorer, candidate support, tree allocation,
prompts, checkpoint, or budgets on these validation sets.

## Frozen setup

- Target: `Qwen/Qwen3-4B`
- Target revision: `1cfa9a7208912126459214e8b04321603b3df60c`
- Drafter: `mgoin/Qwen3-4B-speculator.dflash2`
- Temperature: 0
- Budgets: 8, 16, 32, 64 speculative nodes, excluding the root
- Candidate support: the unchanged DFlash2 top-16 lattice
- GPU: NVIDIA A100-SXM4 40GB
- PyTorch / CUDA / Transformers: 2.7.0 / 12.8 / 5.16.1
- Maximum new tokens: 2048
- Acceptance bootstrap: 10,000 paired resamples, seed 20260904
- Throughput definition per cluster: total output tokens divided by total
  measured decode time
- Throughput CI: paired bootstrap of the absolute per-cluster tokens/second
  difference

MATH500, HumanEval, and GSM8K use one problem per cluster. MT-Bench uses one
two-turn conversation per cluster, never an individual decoding round or turn.

## Controlled versus native MT-Bench

The original run is explicitly the **MT-Bench controlled-history evaluation**.
All methods received the same turn-two history, generated by Pairwise B=64.

The cleanup run is the **MT-Bench native-trajectory evaluation**. Each method
and budget generated its own turn-one answer and received that answer in its own
turn-two history. Cross-method target-token equality was not asserted on turn
two because the inputs intentionally differed.

The Pairwise advantage survives native trajectories at every budget. Native
history slightly reduces the B=8/16 gains but does not change the conclusion.

equivalence.

## Generation anomalies and caveats

- BF16/tree-shape argmax differences remain common. Target verification makes
  each committed sequence valid, but methods need not be byte-identical.
- MATH500 and HumanEval quality variation is therefore expected at problem
  boundaries and is reported rather than filtered.
- The controlled MT-Bench run isolates tree allocation under the same history.
  The native run tests policy-induced multi-turn state shift. Both are retained.
- Throughput is prototype throughput on one A100 and includes the Python tree
  builder. It is not a claim about optimized production performance.
- HumanEval reports standard base-test pass@1, not HumanEval+.
